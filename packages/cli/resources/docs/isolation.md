# Sandbox isolation and provider matrix

Zap's sandbox contract (`packages/sandbox/src/contract.ts`) is one interface
over every execution provider. Box is the default (C2); everything else mounts
behind the same contract, and GPUs are opt-in lane plugins (C4).

## Isolation classes

- **vm / microvm** — hardware-virtualized guests (Box, E2B Firecracker
  microVMs, microsandbox KVM). Strongest boundary; kernel is not shared.
- **container** — namespaced Linux containers (Daytona, Cloudflare Sandbox,
  Modal, docker). Shared host kernel; rely on the provider's hardening.
- **process** — a confined host process (`local`, lane confinement via
  systemd-run). Development and self-host only.
- **hyperlight-wasm** — wasm micro-guests for the `wasm` lane.
- **none** — catalog stubs; `acquire()` throws `CATALOG_STUB` before anything
  runs.

## Tiers

- **first-party** — implements the contract, runs the §5.3.1 conformance suite
  (fake-backed in CI, live variant opt-in with the provider's key).
- **catalog-stub** — manifest + docs page + `doctor` row with
  `verified:false`; no execution path. See `docs/providers/*.md`.

## GPU lanes

`modal` mounts only when `Runtime.md.lanes` declares `gpu:<class>` or a media
step declares `gpu` (C4); every acquire uses `purpose:"lane"` and is billed by
the `gpu_second` SKU per class (`packages/sandbox/src/adapters/modal/pricing.json`).
The dispatcher lives in `packages/runtime/src/lanes/gpu.ts`.
